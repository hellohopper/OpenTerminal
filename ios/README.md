# OpenTerminal for iPhone and iPad

A native SwiftUI companion for the existing self-hosted web terminal. Requires iOS/iPadOS 17 or later and Xcode 16 or later. There are no third-party Swift dependencies.

## Run

1. Keep the existing web and API services running at an HTTPS origin your phone can reach. For a Mac Studio backend with home/cellular access, follow the [repo-local service and Tailscale guide](../docs/mac-studio.md). Set `WEB_ORIGIN` to that exact origin and give both web/API processes the same `WEB_PASSWORD` and `WEB_SESSION_SECRET`. Use the web server URL, not the API port; shared API keys remain on the server.
2. Open `ios/OpenTerminal.xcodeproj` in full Xcode and choose the **OpenTerminal** scheme. Select a simulator and Run. For a physical device, select your signing team and a bundle identifier you control under Signing & Capabilities.
3. Enter the web server origin (for example `https://terminal.example.com`) and the same owner password used by the website. HTTPS certificates must be trusted by the device. There is no TLS validation bypass. HTTP is accepted only for loopback development (`http://127.0.0.1:3100` on a simulator); a phone's localhost is the phone itself.

The app pairs through `/api/mobile/session` and sends a device Bearer token plus the expected Origin header on mutations. Remember this device saves the token in a server-scoped, non-synchronizing Keychain item accessible only while this device is unlocked. Passwords and the shared API key are never persisted on the phone. Backend storage contains only token hashes; authorization expires after 30 inactive days and is renewed on use. Revoke phones in native Settings or web UI settings → Devices. Password/session-secret changes invalidate phone tokens. Temporary network errors retain saved authorization and expose a reconnect action. Redirects are not followed and inactive app previews are covered. UserDefaults contains the server address, selected list/portfolio IDs, last top-level tab and chart range; business data remains on the Mac. The portable client retains its older cookie sign-in API for compatibility, but this app uses device authorization.

## Features

- Today: personal briefing, market indexes, headlines and position-only holdings summary.
- Watchlist: choose a backend shared list, add/remove symbols atomically and open native research. **Manage shared lists** creates, copies, renames, deletes and orders lists. Long-press a symbol to move it up or down. Web workspaces share both orders. Deletion requires confirmation; stale rename/delete/reorder requests refresh the latest list for review. The first phone initializes a list from legacy symbols or defaults only on a server that has never had shared lists. Deleting the last list keeps it empty until you explicitly create another.
- Holdings: choose an existing portfolio, inspect positions and open company research. The selected account is remembered for each server; Today identifies that account alongside its holdings summary. If the account is deleted, the next refresh selects an available account or clears the selection when none remain. Values exclude cash and withhold totals for missing, expired, stale or non-USD quotes. Use the full web terminal for transaction management.
- Alerts: create price-above/below, daily-rise/fall and volume-above/below rules, pause/rearm existing rules, and delete a shared rule after confirmation. The type picker changes the input label and example; changing type clears the threshold while retaining ticker and label. Each new alert fires once and can be rearmed. Daily rises accept 0–1000000% and daily falls accept -100–0%, with a keyboard that allows a minus sign. Enter percentages without a percent sign; the numeric value is sent unchanged (3.5 means 3.5%, not 350%). Price and volume thresholds must be positive and at most 1e15. All types reject grouping, unit suffixes and scientific notation before writing. Each rule blocks competing writes while a request is pending and shows its own action error on failure. Native actions include the reviewed revision and restore generation, so edits on another device or a restored rule reject an older request for refresh and review. Deploy the matching backend update before using these checks; missing version fields prompt a backend update. Existing unversioned web actions keep their prior behavior. Confirmed writes update the row and refresh only alerts; an older list response cannot undo that update, and a late acknowledgement preserves a newer version already seen by refresh. Actions and deletion confirmations belong to the signed-in connection, and controls referencing a locally changed rule require review. Pulling to refresh this tab loads only alerts. Unsaved alert drafts and in-flight saves are shared when the editor is reopened within the same session. Leaving asks whether to keep or discard the draft; sign-out or app termination clears it. Acknowledged saves keep newer edits and refresh only the alert list, independently of market/account loading. Old responses cannot alter a new session. Labels are validated without silent truncation. Threshold entry uses the interface locale’s decimal separator and accepts Unicode decimal digits, with a localized example below the field. Alternate separators are rejected instead of guessed. Bounds are checked before floating-point rounding, and nonzero inputs that underflow cannot silently become zero. The submitted type, metric and threshold belong to the same reviewed draft; edits during saving remain a draft, even after changing away from and back to the original type.
- Alert monitoring: Alerts shows the Mac monitor state and the time the phone received that snapshot, its check interval, last check attempt, last reported error and missing quote symbols. A monitor attempt can finish with an error; **Check details** under each rule shows its last successful evaluation time/value and past trigger time separately. Failed refreshes keep the prior snapshot and receipt time for review, including after an acknowledged rule action; older requests cannot replace a newer snapshot or affect another session. Missing monitor data on older backends is shown as unavailable, and sign-out clears it. Ordinary monitor ticks do not invalidate a reviewed pause/delete, while real rule-definition changes still require review. Pause/rearm acknowledgements clear the evaluation time/value to match the backend and keep the past trigger time. This is a read-only view of recorded checks; polling can miss moves between checks.
- Trigger history: open **Alerts → Trigger history** to read the Mac’s saved triggers, 50 at a time, then load older pages or refresh the latest page. Records include the rule snapshot, actual trigger value, quote price/currency, source, quote observation time and Mac recording time. Rules and history distinguish price, daily percentage change and volume; tiny thresholds retain their precision. Deleting a rule keeps its past events, marked as deleted. Tapping a recorded symbol opens research. Failed reads keep loaded rows and offer an explicit retry; a refresh supersedes older requests. History is held only in memory and clears on sign-out. It records successful Mac checks, cannot reconstruct offline moves and does not establish notification delivery.
- Research: native Swift Charts price history, news links, persistent server research notes and the native share sheet for authenticated research links. Quote, chart, news and notes load independently with their own timestamps and retry controls. Changing chart range rejects older responses. Saved research notes can be deleted after confirmation, without changing the current draft, search or pagination cursor. Reopened views share pending deletions and confirmed removals; delayed list responses cannot bring a deleted note back during that session. A delete includes the reviewed version, so a newer edit on another device returns a conflict for refresh and review. Deploy the matching backend update before using native note deletion; missing versions require a backend update. Existing web clients can still delete without a version. Saving a note preserves newer title/body edits, including edits that return to their original text after closing and reopening research. Reopened editors share the pending save and prevent another submission or draft discard during the write. Backend acknowledgement ends saving immediately; each live research model refreshes its own active search independently, without an additional view-triggered request. Older pages are invalidated before those refreshes start, and a list failure does not turn an acknowledged save into a write failure. Editing clears prior save feedback. Drafts are isolated by server and symbol in memory, and a leave prompt offers keeping or discarding them; they clear on sign-out or app termination and are not written to disk.
- Saved layouts: publish a reviewed device snapshot in the website's Sync panel, then choose Settings → Load published layouts. Confirmation captures the source snapshot, target shared list and target version, and names both lists with the actual imported symbol count. Selecting a different list or loading changed source/target data requires another review; an empty source explicitly asks to clear the list. Symbols are normalized and deduplicated, while invalid symbols or more than 150 unique symbols are rejected before writing. Pending imports are shared across reopened Settings and block competing list-management writes. Backend acknowledgement ends importing without waiting for list or market loading; conflicts refresh the target for review and never retry the write automatically. Late acknowledgements preserve newer list data and another active selection. Source loading, import feedback and market errors remain separate. No shared list is created implicitly, and importing does not write or overwrite web layouts.
- Native notifications: register this phone in Settings after configuring APNs and signing. Background delivery uses the existing alert/signal queue and quiet-hour policy; tapping a symbol notification opens native research only when its server origin and paired-device ID match the authorized connection. Revoking the phone removes its native registration.
- Paired devices: Settings identifies the current device and asks before revoking access. Each target shares a pending state while its request runs, blocks duplicate submissions and shows its own failure for an explicit retry. Confirmed revocation updates the cached row before independently refreshing devices; older list responses cannot undo it. Revoking the current device signs out only after acknowledgement. Requests and confirmations belong to their original connection, and list loading/errors stay separate from market data.
- Full research and professional tools remain available through links to the web terminal. That browser has its own login session.

Notes are scoped to the current company’s research entries. They load 50 at a time; **Load older notes** continues from the last loaded cursor. **Search notes** searches titles and full text on the Mac, including records beyond the loaded pages. All whitespace-separated keywords must match the title or body (up to 200 characters / eight keywords); `%`, `_` and `+` are literal characters. **Clear search** returns to the latest notes. Refreshing or saving reloads the first page of the active search. A failed older-page request preserves the visible notes and its retry cursor; starting a new search rejects older responses and preserves any unsaved draft. Searching requires the updated Mac backend; older backends show an update prompt while unfiltered browsing remains available.

Session restoration is scoped to the current connection attempt. Signing out or changing the server discards late authentication responses; a late pairing attempts to revoke only its newly issued token without saving it. Manual sign-in supersedes an older saved-session restore. Duplicate reconnects do not start additional renewals, and canceled restores keep saved authorization without displaying a connection error. Equivalent address edits such as whitespace or a trailing slash keep an active attempt.

The app enters its main interface after authorization succeeds, then loads watchlists, holdings, alerts and briefings independently. A slow or failing data section does not block the other sections; each shows loading, errors and its own last-success time. The app refreshes while active, supports pull-to-refresh and stops periodic work when backgrounded. It distinguishes offline, timeout, unreachable-server and certificate errors and backs off retries. Settings → Server health checks connection, backup status and push configuration without changing server settings. Prices are indicative provider data; market and account responses are not cached to disk. The installed PWA from [the mobile guide](../docs/ui-modes-mobile.md) retains its separate Web Push path. Native UI and app-owned connection feedback support English and Simplified Chinese through the iOS app-language preference; provider content and user records retain their original language. System text sizing is supported, list-management actions stack at accessibility sizes, tickers use an uppercase ASCII keyboard and price fields use a decimal keyboard.

The app remembers the last top-level tab (Today, Watchlist, Holdings or Alerts) and the last research chart range for each server. A new research page starts with that server’s last chosen range. Signing out clears displayed account data and drafts; signing back in restores the view choices after authorization. Account names, holdings, quotes and research content are fetched from the Mac rather than restored from preferences.

Notification registration belongs to the current signed-in server. Signing out clears its feedback, and late permission answers, system callbacks and backend replies cannot update a newer session or start a later settings write. Explicit **Enable native notifications** registers the phone and enables delivery while preserving the current quiet hours, timezone and settings version. Automatic registration only runs with existing permission and configured backend APNs; it never enables server delivery. Duplicate taps are ignored while registration is pending. System token requests are shared, cancelable and time out after 30 seconds; a failed explicit attempt does not carry permission to enable delivery into an automatic retry. Registration runs independently of market refreshes.

Notification taps include the source server origin and paired-device ID, without any authorization token. The app never switches servers from a notification. A cold-launch tap is kept in memory until the selected server's saved authorization succeeds; a matching identity then opens research. The latest tap wins while startup is pending. Sign-out or a server-address change clears the pending target and any research sheet, and a fresh pairing cannot inherit an old device's target. If a temporary connection failure occurs, an explicit saved-device reconnect can finish that pending navigation. No target is stored in UserDefaults or on disk.

Update both the backend and the app for this routing behavior. Older notifications, or alerts from a backend without a valid `WEB_ORIGIN`, remain visible but cannot automatically open research because they lack a verifiable destination. A valid HTTPS origin or loopback development origin is required; a notification never supplies or replaces the app's server address.

## Push signing

The project includes `OpenTerminal.entitlements` with `aps-environment`: development for Debug and production for Release. Use a bundle ID with Push Notifications enabled and a matching provisioning profile from your Apple Developer team. Put the APNs `.p8` key inside the backend checkout's `config/` directory and configure its key ID, team ID, topic and sandbox/production environment as described in the [Mac guide](../docs/mac-studio.md#optional-native-push-notifications). Keys are never embedded in the app. Debug tokens require sandbox; TestFlight/Release tokens require production. Real background delivery must be checked on a signed physical device.

For a personal-team development build without the Push capability, clear the target's Code Signing Entitlements build setting (`CODE_SIGN_ENTITLEMENTS`) locally and leave native notifications disabled. The foreground app and server alert rules still work; APNs requires a team/profile that supports Push Notifications.

## Validate

With full Xcode selected:

```sh
swift test --disable-xctest --package-path ios
xcodebuild -project ios/OpenTerminal.xcodeproj -scheme OpenTerminal \
  -configuration Debug -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath /tmp/OpenTerminalDerived CODE_SIGNING_ALLOWED=NO build
```

The `iOS` GitHub Actions workflow runs those checks on macOS when Actions is enabled for the repository. The portable core tests cover server origin validation, query encoding, device pairing/renewal/Bearer headers, session expiry, network failures, alert writes, provider errors and incomplete holdings valuations. A separate app-model test target compiles the production model/credential adapter and covers startup, stalled requests, independent section failures, retry recovery, logout during refresh and partial health results with an in-memory credential store and simulated network responses.

Local validation in the authoring environment: core tests and SwiftUI source type checking against the installed macOS SDK. That environment has only Command Line Tools, so an iOS SDK build, simulator launch, device networking, touch/VoiceOver checks and signing still need full Xcode. Source type checking is not an iOS simulator build.

For Command Line Tools installations that do not discover the bundled Swift Testing plugin, pass `-Xswiftc -load-plugin-library -Xswiftc /Library/Developer/CommandLineTools/usr/lib/swift/host/plugins/testing/libTestingMacros.dylib` to `swift test`. The exact plugin path depends on the selected toolchain.

## Mac backend contract regression

On macOS with Node.js 22.12+, Swift 6+ and repository dependencies installed:

```sh
npm run test:ios:integration -- --check
npm run test:ios:integration
```

The first command checks prerequisites. The second builds a disposable production API/web stack from current sources under `test-results/ios-integration/run-*/`, chooses unused loopback ports, and runs the production Swift `TerminalAPI` against the actual Next.js proxy and SQLite routes. It verifies incorrect-password handling, pairing, restored credentials, renewal, targeted and self device revocation without revoking another phone, cross-origin write rejection, browser-cookie access, shared watchlist edits/stale replacements/deletion, published-layout watchlist import with stale-target rejection and explicit clearing, price-alert creation/pause/deletion, monitor snapshots and per-rule evaluation/trigger timestamps, clearing evaluation fields on pause while retaining the past trigger, 50-row trigger-history pagination with price/daily-change/volume snapshots that survive rule deletion, locale-specific price entry becoming numeric HTTP values, all six native alert types preserving their metric and signed percentage/volume values, and research note pagination/search/deletion with Chinese, `+`, `%` and `_` characters. Conditional alert actions reject stale revisions and restore generations, validate version parameters, and apply pause/rearm only after review. Conditional note deletion also verifies a stale phone confirmation cannot delete a newer browser edit, rejects invalid versions and safely repeats a completed deletion. Alert and note deletions verify the backend's empty `204` responses as well as the records' removal. Client commands returning no value accept a successful HTTP status without requiring JSON; calls returning data still require a decodable response, and all calls retain HTTP error handling.

Each run generates its own test credentials. No deployment `config/server.json`, `.env`, existing database, launchd job or Tailscale setting is read or changed. Source copies and build output are isolated from the running deployment. External market-provider responses are fixtures; API/proxy/authentication/storage requests use real HTTP. All test database, backup and log paths stay below this checkout. The runner stops its child processes and removes temporary builds/databases on completion or interruption, retaining private logs and `result.json` in the run directory. Treat forced termination such as `kill -9` as an interrupted run that may require manual cleanup of that run's processes and files.

Ordinary `swift test` skips the eleven backend tests; only the harness supplies their disposable origin and credentials. The iOS workflow also runs this contract suite when Actions is enabled and retains diagnostic logs. A passing contract check validates the native client and server protocol on macOS. It does not validate iOS UI rendering, Keychain behavior on a phone, ATS/TLS, Tailscale routing, simulator installation, signing or APNs delivery; those still require full Xcode and/or a physical device.

## Distribution

The repository includes a shared scheme, app icon and UserDefaults required-reason privacy manifest. Before a TestFlight/App Store upload, use your Apple Developer team, configure signing and App Store Connect metadata for your deployment, and verify on a real device. This repository does not contain signing credentials or claim that the app is already distributed. Apple's [app icon guide](https://developer.apple.com/documentation/xcode/configuring-your-app-icon) and [required-reason API documentation](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype) describe the relevant project resources.
